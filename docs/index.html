Systems design

Distributed in-memory key-value store

A Linux-native C++ cache built around epoll, frame-based TCP I/O, and a Redis-inspired command model.

What is implemented

Non-blocking TCP I/O
Per-worker epoll loops
TTL and memory policies
Concurrent CLI tools
Binary frame limits
Replication not implemented

Current architecture

The server is built around a single acceptor thread and a pool of worker threads. The acceptor accepts new TCP connections and hands them to workers in round-robin order. Each worker owns an epoll instance and a connection map, making the request path concurrent without a thread-per-connection model. Workers share one mutex-protected in-memory map. The mutation backlog is recorded locally and is not streamed to followers.

Request lifecycle

sequenceDiagram
    participant C as Client
    participant W as Worker
    participant D as Dispatcher
    participant S as Store
    participant B as Backlog

    C->>W: framed request
    W->>W: read until EAGAIN
    W->>D: execute command
    D->>S: lock store / mutate state
    S-->>D: result
    D->>B: record mutation
    D-->>W: response
    W-->>C: response frame

Core design choices

  • Binary framing: each request is length-prefixed to avoid text parsing and support fast partial reads.
  • Memory policy: approximate key/value size accounting supports write rejection or an LRU scan under maxmemory; this does not cap total process RSS.
  • TTL: expired keys are lazily pruned during store operations.
  • Lock granularity: a single store mutex protects the shared map; sharding is a future optimization.
  • Replication: mutations are recorded in a local backlog, but follower synchronization and failover are not implemented.
